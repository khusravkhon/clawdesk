# Этап 4: фиксированные личные напоминания
## Область

Добавлены только новые одноразовые напоминания владельцу. Они хранятся в panel SQLite отдельно от OpenClaw cron. Создание владельцем — единственный способ добавить такую доставку; миграция не создаёт и не отправляет напоминаний. Корпоративный режим запрещает API и обработку очереди.

Действия «сделано / пропустить / позже» относятся к конкретной occurrence. «Позже» атомарно закрывает исходную occurrence и создаёт новую, связанную parentId. Повтор того же запроса после потери ответа или перезапуска возвращает результат без повторного snooze. Эти действия не отменяют и не редактируют существующие повторяющиеся AI-расписания. Тихие часы действуют только на новую очередь фиксированных напоминаний, не на все существующие Telegram-боты или cron.

## Протокол и гарантии

Проверен первичный код OpenClaw 2026.8.1 из локального npm-архива `openclaw-curl.tgz`: `package/dist/server-methods-DOqyd9US.js` маршрутизирует метод `send` в `send-CcjRWFvK.js`. Последний содержит исходный регион `src/gateway/server-methods/send.ts`, обработчик send, idempotencyKey, in-flight dedupe и ответ с `messageId`. Dedupe хранится в `context.dedupe`, поэтому это не доказательство сквозной долговечной exactly-once доставки после рестарта Gateway.

Panel вызывает только native `send` с фиксированным текстом, channel telegram и стабильным ключом `clawdesk-reminder:<occurrenceId>`. Нет agentTurn, systemEvent или генерации моделью. Получатель определяется исключительно `TelegramService.ownerDelivery()`: этот метод использует `#owner()` с accountId default, включая legacy null binding. Поэтому send использует accountId default; чужие аккаунты и произвольный адрес из браузера не принимаются.

Перед сетевым вызовом фиксируется `sending`. Подтверждённый messageId означает `sent`: провайдер принял отправку; прочтение получателем не утверждается. Исключение, ответ без messageId или восстановленная после crash строка sending становятся `unknown`. Такие строки автоматически не повторяются: отправка могла уже состояться. Потеря процесса после фактического send, до записи результата, также приводит к unknown при следующем старте. «Позже» для unknown является явным новым запросом пользователя и потенциально может создать ещё одно сообщение.

Отсутствие Gateway или привязанного владельца до отправки сохраняет pending. Обычный срок доставки — 24 часа после dueAt. Тихое окно продлевает сохранённый expiresAt максимум до dueAt + 48 часов, чтобы ближайшее разрешённое окно не терялось при ночной задержке; бесконечное mute не сохраняет очередь бесконечно. После срока — expired без отправки. Нормальное разрешённое окно при недоступном Gateway не гарантирует доставку.

Время сравнивается по фактическим локальным часам указанной IANA timezone перед отправкой каждой occurrence, включая повтор и пропуск часов DST. Интервал start inclusive / end exclusive; start=end означает весь день. Настройка timezone не зависит от timezone контейнера. Tick каждые 15 секунд, до 50 старейших due occurrence за проход. CAS-предикаты не позволяют устаревшей выборке перезаписать уже отправленную/закрытую строку. Список приоритизирует ближайшие open; предел 200 честно отмечается partial.

## API и хранение

- GET/POST `/api/reminders` — список / создание с requestId UUID.
- PUT `/api/reminders/preferences` — тихие часы.
- POST `/api/reminders/:id/action` — done, skip, snooze с requestId UUID.
- Миграция `0009_personal_reminders.sql`; настройки тихих часов в существующей settings.
- Singleton ReminderService запускается вместе с BFF, recover переводит неопределённые sending в unknown, shutdown ждёт текущий проход.

## Проверка

`node node_modules/vitest/vitest.mjs run test/personal-reminders.test.ts` — 23 проверки: пустая очередь; native send без LLM; stable key и повтор tick; повтор create/action; отсутствие владельца; company; offline/reconnect; expiry; unknown без replay; crash между send и записью результата; настоящее закрытие/открытие отдельной временной SQLite; stale batch; batch cap; partial; action во время отправки; тихие часы, DST, конечное продление и переход через начало тихих часов/expiry во время предыдущей медленной отправки.

Shared сборка и BFF TypeScript проверены direct node CLI с Windows sandbox escalation. В тестах только fake Gateway и временные/оперативные базы; настоящим получателям ничего не отправлялось. Рабочая установка не обновлялась. Коммит и push не выполнялись. Live end-to-end подтверждение после обновления установки остаётся отдельным действием владельца.
