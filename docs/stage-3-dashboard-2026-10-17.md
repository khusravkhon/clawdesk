# Этап 3: полная и ограниченная история расписаний

Дата: 2026-10-17. Изменения исходников; личные контейнеры и Telegram-боты не перезапускались и не изменялись.

## Проблема и поведение

Обзор запрашивал только последние 200 записей `cron.runs`, хотя экран предлагал периоды до 90 дней. Теперь BFF проходит страницы истории и каталога расписаний по поддержанному `offset`, по 200 элементов. Предел работы: 50 страниц на каждый метод (до 10 000 строк истории и 10 000 задач), общий бюджет 8 секунд на загрузку обоих наборов; каждый RPC получает оставшийся `timeoutMs`. При пересечении начала периода отсортированной историей дальнейшие страницы не читаются.

Если история целиком помещается в эти ограничения и ответы согласованы, выводится процент успешных запусков. Лимит, отказ следующей страницы, отсутствующие или противоречивые метаданные, повтор страницы/курсор, изменившийся total/revision/порядок и неоднозначные дубли дают явный частичный результат; процент успеха скрывается. Отказ первой страницы не превращается в нулевое число запусков: раздел schedules возвращается null с ошибкой. Успех других разделов от этого не зависит.

Дедупликация использует `jobId + runId`, затем `jobId + runAtMs`, и только для старых записей `jobId + ts`; при нескольких страницах без надёжного идентификатора результат помечается неполным. Для обновлённой записи сохраняется версия с большим ts. Постоянно меняющийся Gateway не блокирует запрос бесконечно. В offset-протоколе истории нет snapshot token: `historyComplete` означает отсутствие обнаруженной неполноты в ответах, а не атомарный снимок параллельно изменяющейся базы.

Системные задачи по-прежнему исключаются общей политикой `isSystemJob`. Записи отсутствующих в текущем каталоге заданий не объявляются пользовательскими вслепую: для таких записей в периоде ставится `historyReason: unknown_jobs`, интерфейс поясняет, что это могут быть удалённые задачи и приведены итоги для текущих расписаний.

Фильтрация использует завершённые записи (`ts`), выбранные календарные дни часового пояса и захваченный в начале запроса `now`. Будущее, включая последующую часть текущего дня, не попадает в историю. Конец дня и границы периода определяются локальной датой, не UTC. Даты строятся календарно, поэтому переход DST не повторяет и не теряет день.

Dashboard polling теперь single-flight. Смена периода инвалидирует старый ответ и ставит последнюю выбранную загрузку в очередь. Скрытая вкладка не начинает опрос; возврат видимости обновляет данные. При уничтожении компонента удаляются interval и visibility listener, поздние ответы не применяются.

## Подтверждение реального API

Read-only проверка первичного кода установленного Gateway выполнена через `docker exec clawdesk-local-gateway-1` с escalation. Читались только исходники пакета и версия, личные cron записи, summary и токены не печатались. `/app/package.json` вернул **2026.8.1**.

- `/app/dist/src-CwDR-7yt.js:7501–7517`: `CronListParamsSchema` включает `includeDisabled`, `limit` 1–200, `offset >= 0`, `includeDeliveryPreviews`.
- Там же `:7610–7632`: `CronRunsParamsSchema` включает `scope`, `runId`, `limit` 1–200, `offset >= 0`, `sortDir`.
- `/app/dist/cron-DEtsrllq.js:436–455`: ответ каталога содержит `snapshotRevision`, `total`, `offset`, `limit`, `hasMore`, `nextOffset`; revision вычисляется по полному стабильному каталогу.
- `/app/dist/list-snapshot-revision-BZmZTgwt.js:390–392`: `compareHistoryRows` сортирует по `entry.ts`, затем `task.createdAt` и `taskId`. Поэтому фильтр периода и остановка используют **ts**, а не runAtMs. `runAtMs` служит дополнительным идентификатором старого запуска.
- Там же `:401–435`: история возвращает `entries`, `total`, `offset`, `limit`, `hasMore`, `nextOffset`; snapshotRevision у истории нет.

Пример read-only команды воспроизведения (путь относится к версии существующего образа):

```powershell
docker exec clawdesk-local-gateway-1 sh -lc 'grep -n -A 45 "const CronListParamsSchema" /app/dist/src-CwDR-7yt.js'
```

Из каталога `packages/shared`: `node node_modules/typescript/bin/tsc -p tsconfig.json` — успешная сборка DTO.

Из `apps/bff`:

```powershell
node node_modules/typescript/bin/tsc -p tsconfig.json --noEmit
node node_modules/vitest/vitest.mjs run test/dashboard.test.ts test/dashboard-service.test.ts test/cron-history.test.ts test/dashboard-polling.test.ts
```

28 профильных тестов: 4 файла. Проверяются 451 пользовательский запуск на трёх страницах, каталог из 201 задания, системные и удалённые задачи, отказ первой и последующей страницы, legacy metadata, повтор страниц/курсор, дубли и обновления, изменяющийся total, предел 50 страниц, ранняя остановка по периоду, точная локальная полночь/будущее/DST, single-flight, устаревший ответ периода и очистка lifecycle.

Polling тесты исполняют transpile фактического script-фрагмента DashboardView с подменёнными сетевыми вызовами, часами interval и visibility lifecycle; не имитируют браузерную отрисовку графиков. Production Vue typecheck и Vite build отдельно подтверждают сборку компонента.

Из `apps/web`: `node node_modules/vue-tsc/bin/vue-tsc.js --noEmit` и `node node_modules/vite/bin/vite.js build --logLevel error`.

Реальные длительные истории пользователя не сканировались для теста нагрузки; программные проверки используют фиксированные данные. Чистая установка и выкатывание образа вне этой проверки. Коммит и push не выполнялись; изменения этапов 1–2 сохранены.
