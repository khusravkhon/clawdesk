# Компания: понятное создание проектов и защита бизнес-правил

Дата: 18.10.2026. Обновлено: 04.11.2026. Статус: отдельное ТЗ, дополнение к [структуре компании и интерактивным командам](company-organization-and-interactive-teams.md). Частично реализованы P1–P3: каталог, новая/существующая папка внутри разрешённого корня установки, сохраняемый пошаговый черновик требований, сводка ответов, отдельные бизнес-правила с версиями и согласованием владельцем в панели. Добавлена основа трассировки: приёмочные сценарии для точной версии правила, версии сценариев, текстовые ссылки на проверки и журнал ручных результатов. Сделаны P4–P5 для одного шаблона («Доска задач») и первый срез P6: тесты созданного приложения запускаются в изолированном контейнере, приёмочный сценарий связывается с тестом и получает его результат, изменённый тест не засчитывается. Сделаны задачи QA и разработчика (P6.2) и изменение уже реализованного правила (P6.3): отчёт о влиянии со старой и новой версией, замена тестов только этого правила при защите остальных тест за тестом, подтверждение владельца о существующих данных, блокировка устаревшей задачи и откат последней принятой задачи. Добавлен опрос с моделью главного агента: вопросы по 1–3 с примерами, предположения на решение владельца, пересказ первой версии. Добавлены проверка противоречий между правилами моделью (открытое противоречие блокирует задачу по его правилам до решения владельца) и поиск правила по фразе пользователя по словам. Подробности проверки и границы текущей версии — в [журнале реализации](company-implementation-progress.md).

## 1. Задача

Обычный пользователь описывает, что хочет создать и как должно работать его дело. ClawDesk помогает превратить описание в понятные требования, подобрать соразмерную техническую основу, подготовить проект в выбранной папке и выполнять изменения с проверками бизнес-правил.

GitHub, знание языков программирования и готовая команда не являются условиями создания проекта. Можно начать с нового проекта на компьютере, подключить существующую папку, работать на сервере и позднее добавить репозиторий. Отдельный агент тоже может работать над проектом без отдела и команды.

Основной сценарий — минимальное число понятных шагов. Технические решения доступны в раскрываемом блоке «Технические подробности». Система объясняет последствия и неопределённости, не обещает, что любой сгенерированный проект выдержит любую нагрузку.

## 2. Подтверждённая исходная реализация

Сейчас `CreateTeamRequest` в `packages/shared/src/teams.ts` требует GitHub URL и токен. `TeamService.create()` проверяет GitHub и вызывает `bridge.teamClone()`. `deploy/clawdesk-teams.mjs` создаёт отдельную копию репозитория для разработчика. Это не мастер новых локальных проектов.

Песочницы существующих проектных агентов работают без сети и не получают GitHub-токен. Новая функция не должна ради удобства убрать эту границу: загрузка зависимостей и работа с GitHub выполняются отдельным контролируемым посредником.

Переиспользуются проекты/отделы из основного ТЗ, grant-политики, задачи, агентные профили, saga, bridge, журнал и существующие подключения. Бизнес-данные создаваемого приложения не хранятся вперемешку с метаданными панели.

## 3. Каталог проектов и группировка

На уровне компании — «Все проекты» с фильтром по отделу, месту выполнения и состоянию. Внутри отдела — его проекты и команды. Показать отдельные связи: «Проект» и «Работающие над ним команды»; не путать команду с репозиторием или директорией.

Карточка проекта: название, понятная цель, отдел или «Без отдела», работающие агенты/команды, место выполнения, источник файлов, состояние требований/реализации, блокировки, следующий шаг. При нескольких командах не показывать дубликаты проекта.

Состояния подготовки: черновик → уточняются требования → требуется решение → план согласован → подготовка → готов к работе / ошибка. Отдельно хранится состояние выполнения задач. Проект с незавершённым опросом можно сохранить и продолжить позже.

Отдел, команда, GitHub и технический стек не обязательны для сохранения черновика. Архивирование карточки не удаляет папку и удалённый репозиторий.

## 4. Мастер для обычного пользователя

### Шаг 1. Что вы хотите сделать

Варианты: внутренняя панель; сайт; CRM/учёт клиентов; веб-приложение; мобильное приложение; API/автоматизация; другой проект; продолжить существующий. Выбор помогает задавать вопросы, но не фиксирует язык и архитектуру.

Первый вопрос: «Опишите своими словами, для кого приложение и какую задачу оно решает». Можно приложить пример, документ и изображение. Материалы рассматриваются как данные, а не как разрешение исполнить инструкции внутри них.

### Шаг 2. Как это должно работать

Задавать вопросы небольшими порциями, по 1–3 за шаг, использовать примеры и варианты ответа. Не требовать сразу полного ТЗ. Показывать прогресс и позволять изменить предыдущий ответ.

Темы опроса: пользователи и роли; основные действия; данные; правила и исключения; статусы и переходы; доступ и запреты; внешние сервисы; уведомления; отчёты; ожидаемое число пользователей и одновременная активность; устройства; файлы/медиа; работа без интернета; импорт; чувствительность данных; бюджет эксплуатации и обслуживания.

Не задавать одинаковые вопросы повторно, если ответ уже есть в описании. Догадки помечать как предположения. Отсутствие ответа на вопрос о нагрузке не трактовать как бесконечную нагрузку или нулевых пользователей.

### Шаг 3. Проверка понимания

Показать простой пересказ: «Мы создаём…», кто пользуется, что входит в первую версию, что не входит, 3–5 основных сценариев и нерешённые вопросы. Для каждого сложного правила дать конкретный пример.

Пример: «Скидку до 10% менеджер назначает сам. Выше — только после согласования руководителем. При отмене заказа товар возвращается в остаток». Рядом — примеры разрешённого и запрещённого действия.

Пользователь подтверждает смысл, а не сложную техническую спецификацию. При противоречии, например «любой может менять заказ» и «заказ меняет только владелец», система предлагает выбрать правило до реализации затронутой функции.

### Шаг 4. Предлагаемая основа

Предложить один основной вариант с объяснением «почему подходит», сложностью поддержки, требованиями к компьютеру/серверу и известными ограничениями. Альтернативу показывать только при значимом компромиссе. Не превращать шаг в длинный список фреймворков.

В техническом блоке: язык, frontend/backend, хранилище, границы модулей, проверки, работа с фоновой очередью и соединениями, версия шаблона, путь будущего расширения. Человек с опытом может изменить решение; после изменения пересчитать связанные требования.

### Шаг 5. Где хранить и выполнять

Сначала показать выбранную установку: «Этот компьютер» или конкретный сервер. Затем предложить «Новая папка», «Существующая папка» или «Из GitHub». Для нового проекта GitHub можно добавить следующим необязательным шагом.

Показать итоговый путь, доступ агентов, объём изменений, наличие внешних запросов и что будет создано. Кнопка «Подготовить проект» выполняет показанный план. Приложение не пишет в произвольную папку по пути из ответа модели.

### Шаг 6. Результат

Карточка проекта с требованиями, проверками, файлами и командой. Действия: открыть папку; прочитать правила; запустить проверки; назначить агентов/команду; подключить GitHub; продолжить подготовку. Создание карточки не означает, что готово всё приложение или оно развёрнуто в интернете.

Показать отдельные результаты: требования подготовлены; основа создана; бизнес-правила проверены; приложение запускается в изолированном preview; готово к развёртыванию. Не заменять все эти состояния одной зелёной галочкой «готово».

## 5. Папки, новый и существующий проект

Для новой папки используется выбранный пользователем разрешённый корень. Проверять реальный путь, symlink/junction, выход через `..`, пересечение с системными папками и другими проектами. Агент получает рабочую область проекта и необходимые права, а не доступ ко всему диску.

Существующую папку сначала исследовать без изменений: файлы, Git-статус, текущий стек, инструкции репозитория, тесты, файлы зависимостей и возможные секреты. Не переписывать проект под новый шаблон. В существующем коде соблюдать его соглашения и сохранять комментарии. Секреты не включать в описание модели и внешнюю публикацию.

Перед записью показать план изменений. Не удалять пользовательские файлы, не переинициализировать существующий Git, не переписывать незакоммиченные изменения, не выполнять reset/clean ради подготовки. Для важного преобразования нужна восстановимая контрольная точка; Git может использоваться локально без аккаунта GitHub.

Одна файловая рабочая область — один активный пишущий исполнитель. Для параллельных разработчиков использовать изолированные рабочие копии/ветки и управляемое объединение. До внедрения такого механизма запрещать одновременную запись, а не надеяться на дисциплину промпта.

Preview и тесты запускаются изолированно с лимитами ресурсов, без общих токенов панели. Выполнение package scripts и установка зависимостей могут запускать чужой код; для них отдельный контролируемый этап, ограниченная сеть и видимый статус. Служебный порт preview не публиковать в интернет автоматически.

## 6. GitHub как дополнительная возможность

Три независимых операции: подключить существующий репозиторий; создать новый; опубликовать/синхронизировать локальные изменения. Для новой GitHub-интеграции сначала проверить поддерживаемый способ авторизации и минимальные полномочия — текущий токен отдельного репозитория не обязательно позволяет создавать новые репозитории.

Создание нового репозитория показывает владельца/организацию, имя, видимость и содержимое первой отправки. По умолчанию предлагается приватный репозиторий; если это недоступно выбранному аккаунту, не менять его на публичный без решения пользователя.

План создания/первой отправки подтверждается отдельно. `.env`, ключи, локальные БД, приватные документы, артефакты и файлы, исключённые пользователем, не отправляются автоматически. Сгенерировать подходящий `.gitignore`; дополнительно проверять содержимое, а не полагаться только на расширения.

При сбое GitHub локальный проект остаётся рабочим. Повторная попытка сначала проверяет результат предыдущей: не создаёт второй репозиторий и не перезаписывает чужой. Если репозиторий уже создан, сообщить его адрес и точный незавершённый шаг. Не удалять его автоматически как компенсацию.

Показывать расхождение локальных и удалённых изменений. Никакого скрытого force push. Загрузка, обновление, конфликт, подготовка изменений и открытие PR имеют отдельные состояния. Полная двусторонняя автоматическая синхронизация не входит в первую локальную версию.

## 7. Как выбирать техническую основу

Выбор строится на правилах приложения, данных, ролях, интеграциях, нагрузке, среде запуска и возможностях сопровождения. Предпочитать минимальную достаточную сложность с разделением бизнес-логики и инфраструктуры.

| Потребность | Принцип выбора |
| --- | --- |
| Небольшая внутренняя панель | Простое развёртывание, понятные модули и авторизация, тестируемые правила; не нужны микросервисы по умолчанию |
| CRM со сложными переходами и правами | Явные доменные границы, транзакции, роли, история, интеграционные проверки; модульный монолит — рассматриваемый начальный вариант |
| Чат / обновление данных в реальном времени | Учесть соединения, восстановление, доставку и нагрузку; наличие WebSocket не определяет язык backend само по себе |
| Мобильное приложение | Устройства, камера/уведомления, offline, публикация в магазинах и backend; не выдавать веб-страницу за готовую мобильную сборку |
| Существующий проект | Сохранить подходящую основу; миграция языка/архитектуры — отдельная задача с причиной и планом перехода |

Vue/Node.js, Vue/ASP.NET Core и другие сочетания могут быть профилями каталога, но не жёстким правилом «CRM = C#» или «сложный frontend = Angular/FSD». Clean Architecture, FSD, CQRS и паттерны вводятся ради подтверждённой задачи, а не количества терминов. В первой версии поддержать один полноценно проверенный web-профиль; остальные варианты помечать «планирование поддержано, автоматическая подготовка пока недоступна», пока они не пройдут приёмку.

Каталог профилей версионируется: происхождение шаблона, лицензия, совместимые runtime, поддерживаемые ОС, pinned-зависимости/lockfile, состав тестов и контрольные примеры. Перед выпуском профиля проверить актуальные официальные рекомендации и известные проблемы зависимостей. Модель не скачивает и не исполняет произвольный шаблон, найденный в интернете.

Подбор основы — задача с лимитом стоимости и числом уточнений. Пользователь видит, что нужен подключённый ИИ; при отсутствии подключения можно сохранить описание и выбрать проверенный профиль вручную. Перегенерация архитектуры при каждом открытии карточки запрещена.

## 8. Требования и проверяемые бизнес-правила

Хранить версионированный набор требований с постоянными ID. Для каждого правила: источник/автор, формулировка простыми словами, роль, предусловия, действие, ожидаемый результат, исключения, примеры, статус согласования и ссылки на проверки.

Пример:

| Поле | Значение |
| --- | --- |
| ID | BR-ORDER-003 |
| Правило | Менеджер назначает скидку до 10%; больше — после одобрения руководителем |
| Разрешённый пример | Менеджер назначает 10% активному заказу |
| Запрещённый пример | Менеджер назначает 11% без одобрения |
| Исключение | Пользователь не имеет доступа к этому заказу — изменение запрещено при любом размере скидки |
| Проверки | Граничные 0/10/11%, роли, чужой заказ, запись решения руководителя |

Цепочка трассировки: требование → критерии приёмки → тесты → реализация → результат проверки. Отчёт объясняет пользователю, какие правила подтверждены, какие ещё не проверены и почему.

При конфликте правил затронутая реализация блокируется до решения. Тестирование не ограничивается happy path: нужны границы, отказы доступа, ошибочные входные данные, повторные запросы и важные переходы состояния.

## 9. Работа команды через тесты

Процесс: пользователь согласовал правило → аналитик/тимлид уточнил критерии → QA подготовил проверяемые сценарии → разработчик реализовал → проверки выполнены → независимое ревью → понятный итог владельцу.

Для нового проверяемого правила сначала создаётся содержательная проверка, которая падает по ожидаемой причине; затем код делает её проходящей. Ошибка окружения, сборки или отсутствующий тестовый runner не считаются доказательством корректного падающего теста.

Уровни проверок: быстрые unit-тесты доменных правил; интеграционные проверки БД/API/прав; немного сквозных сценариев основных пользовательских потоков. Снимки интерфейса и тесты, повторяющие реализацию, не заменяют проверку правил. Покрытие строк — вспомогательный сигнал, а не гарантия.

Новый сотрудник или агент перед изменением получает правила, связанные тесты, инструкции репозитория и принятые решения. Обязательный набор проверок нельзя молча удалить, пропустить, ослабить assertion или заменить snapshot ради зелёного статуса. Изменение теста, защищающего бизнес-правило, должно ссылаться на согласованное изменение этого правила и проходить отдельное ревью.

Генерация кода и проверок одной моделью имеет риск общей ошибки. Смысл правила подтверждает владелец; ревью использует независимый запуск/роль, а критические граничные примеры фиксируются явно. Тесты снижают риск регрессий, но не обещают отсутствие всех ошибок, защиту от любой атаки или любую производительность.

## 10. Изменение бизнес-логики и защита от регрессий

Пользователь говорит: «Теперь скидка 15% доступна только руководителю». Система находит BR-ORDER-003, показывает прежнее/новое правило, затронутые экраны, API, тесты и данные. Старую версию не затирать.

После согласования создаётся новая версия правила и задача изменения. Добавить проверки нового поведения, сохранить проверки незатронутых сценариев. Миграция данных проектируется отдельно от изменения кода. При сомнительной совместимости не продолжать выпуск автоматически.

Статусы проверок: пройдено, ошибка поведения, не запускалось, блокировка среды, нестабильный тест. Не заменять неизвестный результат успехом. Итог для пользователя: что изменилось, какие правила проверены, что требует решения и как вернуть предыдущую рабочую версию.

Локальный проект получает воспроизводимую команду проверок и историю прогонов. После подключения GitHub можно предложить CI, но наличие CI не означает настроенную защиту ветки. Если права/тариф провайдера не позволяют сделать обязательные проверки, честно показать ограничение; выпуск из панели блокируется собственной политикой до завершения требуемых проверок.

## 11. Компьютер, сервер и фоновые задачи

Выбор места выполнения независим от личного/корпоративного режима. Оба режима работают локально и на сервере. Личный ассистент, которому нужны регулярные напоминания и фоновая работа при выключенном ноутбуке, ориентирован прежде всего на постоянно включённый сервер.

| Ситуация | Ожидаемое поведение |
| --- | --- |
| Компания на компьютере | Агенты работают в разрешённых локальных папках, пока доступен backend/Docker |
| Компания на сервере | Агенты работают с серверными ресурсами, независимо от открытого окна desktop |
| Закрыто окно панели | Работа доступного backend продолжается |
| Выключен компьютер с локальным backend | Выполнение остановлено; задачи не изображаются работающими |
| Сервер недоступен | Показать недоступность; новые действия не считаются выполненными |
| Desktop подключён к серверу | Выбор папки относится к серверу; папка клиента не монтируется автоматически |

Переход с компьютера на сервер — явный мастер переноса: что копируется, размер, права, секреты, проверка совместимости, подтверждение назначения и результат проверки. Перенос одного проекта не равен восстановлению всей установки. Одновременный запуск двух копий расписаний/ботов не включать автоматически.

Для MVP папки на сервере выбираются из разрешённых корней, а импорт с компьютера — явной загрузкой с контролем объёма и содержимого. Постоянный удалённый агент файловой системы и автоматическая синхронизация любых папок — последующее расширение.

Автозапуск после перезагрузки проверяется отдельно для поддерживаемой среды. После паузы задачи сверяются с фактическими запусками и продолжаются по политике, без повторной отправки уже выполненных внешних действий.

## 12. Производительность и эксплуатация создаваемого проекта

Опрос фиксирует ожидаемую нагрузку и допустимые задержки основных операций. Если чисел нет, предложить небольшой проверяемый сценарий и отметить неизвестность. Нельзя писать «готов к большой нагрузке» без описания стенда, входных данных и результатов.

Профиль закладывает валидацию, корректные ошибки, структурированные журналы без секретов, миграции БД, health-check, конфигурацию окружения и воспроизводимую сборку. Индексы и запросы выбираются по реальным данным и сценариям, а не по универсальному списку оптимизаций.

Репликация, шардинг, оркестрация, резервирование инфраструктуры и промышленное развёртывание требуют отдельного плана и проверки специалистом. Мастер объясняет это обычными словами и готовит список требований к размещению. Он не покупает сервер, не публикует сервис и не обещает SLA по факту генерации кода.

## 13. Данные и результат мастера

Использовать общий `projects` основного ТЗ. Дополнения: `executionTargetId`, режим источника, версия требований, версия технического решения, состояние подготовки. Файловые пути и удалённый репозиторий хранить отдельными ресурсами с проверяемыми grants.

Проект контракта: `project_briefs`, `project_requirements`, `requirement_versions`, `architecture_decisions`, `project_workspaces`, `project_repositories`, `project_check_runs`, `requirement_check_links`, `project_preparation_jobs`. Это не существующие таблицы; точное минимальное разбиение выбрать при реализации, не дублируя действующие задачи и журнал.

Человекочитаемые артефакты в выделенной папке документации проекта: описание и границы; бизнес-правила; сценарии приёмки; техническое решение; инструкции запуска/проверок; журнал решений. Не перезаписывать существующий README или инструкции при импорте: сначала показать предлагаемые изменения. Секреты и персональные данные не включать в общую документацию и Git по умолчанию.

Метаданные мастера и правила включаются в backup ClawDesk. Внешняя пользовательская папка не считается автоматически включённой в backup панели: показывать, включены ли файлы проекта, где хранится отдельная копия и как её восстановить. Для проекта на другом сервере ссылки недостаточно.

Операции подготовки идемпотентны, с прогрессом, отменой и восстановлением после перезапуска. Ошибка не удаляет исходную папку и не скрывает уже созданный GitHub-репозиторий. Точные границы отката показывать пользователю.

## 14. Поэтапная реализация

Нумерация P0–P9 относится только к этому ТЗ. Основные этапы 0–3 из ТЗ компании дают базовую структуру и повторно используемый каталог проектов. До готовности полной иерархии проект допускается на уровне компании; мастер не требует сначала реализовать виртуальный офис.

| Этап | Результат | Критерий завершения |
| --- | --- | --- |
| P0. Границы и исследование | Матрица local/server, разрешённых папок, sandbox, авторизации GitHub и поддержки профилей | Подтверждены реальные операции и ограничения; нет обещаний неподдерживаемой генерации |
| P1. Проект без GitHub | Общая карточка проекта, новая/существующая папка, отдел/команда по желанию | Проект сохраняется без токена; исходные данные не изменяются при ошибке |
| P2. Описание и сценарии | Пошаговый опрос, пересказ, черновики, явные неизвестные | Пользователь понимает первую версию; перезапуск сохраняет ответы |
| P3. Правила | Постоянные ID, версии, примеры, согласование, конфликты | Нельзя начать затронутую функцию при противоречащих правилах |
| P4. Подбор основы | Один проверенный web-профиль, понятное решение и технические подробности | Выбор обоснован требованиями; альтернативы не выдаются за готовую генерацию |
| P5. Подготовка локальной основы | План файлов, изолированная генерация/сборка, ограниченный preview | В новой папке воспроизводятся запуск и проверки; импорт не переписывается шаблоном |
| P6. Изменения через проверки | Связи правило → тест → код, задачи QA/разработчика, результаты | Намеренная поломка правила обнаруживается; старые сценарии остаются защищены |
| P7. GitHub | Импорт, новый приватный репозиторий, явная первая отправка и PR | Нет утечки секретов; сбой сохраняет проект; повтор не создаёт дубликат |
| P8. Сервер и перенос | Аналогичный сценарий на сервере, явная передача проекта, восстановление jobs | Сервер не читает клиентскую папку без передачи; рестарт не дублирует действия |
| P9. Сквозная приёмка | Понятный мастер, регрессии, backup/restore, поддержанные среды | Пройдены сценарии следующего раздела; указаны ограничения и инструкция сопровождения |

Первый полезный срез этого направления — P0–P2: проект в папке без GitHub и понятное описание, которое можно сохранить. Выбор сложной архитектуры, новый репозиторий и автоматическая реализация бизнес-логики добавляются следующими отдельными изменениями.

## 15. Приёмка

1. Пользователь без GitHub и без команды описывает простую панель, сохраняет черновик и создаёт проект в новой разрешённой папке.
2. Пользователь указывает существующий проект с незакоммиченными изменениями: система сначала читает, сохраняет файлы/стек/историю и предлагает ограниченный план.
3. Папка вне разрешённого корня, junction/symlink наружу и попытка открыть чужой проект запрещены реальной проверкой доступа.
4. Пользователь не знает языков: получает пересказ задач и один объяснённый вариант основы; технические детали доступны по желанию.
5. Выбор «CRM» или «чат» сам по себе не навязывает язык, FSD, микросервисы или обещание высокой нагрузки.
6. Противоречивые права/статусы в описании выявляются; функция остаётся заблокированной до согласования.
7. Правило BR-ORDER-003 защищено граничными проверками. Намеренное разрешение менеджеру чужой скидки ломает тест и не проходит приёмку.
8. Изменение правила создаёт новую версию и связанные проверки. Агент не может просто удалить падающий тест и объявить успех.
9. Перезапуск на опросе, генерации, тестах и внешнем запросе сохраняет прогресс и не перезаписывает пользовательскую работу.
10. Подключение GitHub не требуется для локальных проверок. Его сбой не блокирует локальную работу; повторное создание репозитория не даёт дубликат.
11. Перед отправкой показаны видимость и файлы; `.env`, тестовый секрет и приватный документ не публикуются.
12. Параллельные разработчики изолированы или второй получает очередь. Они не пишут одновременно в одну и ту же рабочую область.
13. Работающая серверная установка продолжает задачу после закрытия desktop. Выключенная локальная установка не отображается как выполняющая задачу.
14. Копия проекта и копия установки различимы; проверено восстановление метаданных и самих файлов для заявленного варианта.
15. В отчёте производительности есть условия и результат проверки; неподтверждённая нагрузка явно отмечена. Нестабильный тест и ошибка среды не выглядят как успех.

## 16. Проверенные источники и открытые решения

Официальные источники, просмотренные 18.10.2026: [Microsoft: варианты архитектуры веб-приложений](https://learn.microsoft.com/en-us/dotnet/architecture/modern-web-apps-azure/common-web-application-architectures) описывает простое развёртывание монолита и отделение бизнес-ядра для тестирования; [Node.js: введение](https://nodejs.org/en/learn/getting-started/introduction-to-nodejs) описывает событийную обработку I/O. Эти материалы помогают обосновать соразмерный выбор; они не подтверждают производительность будущего сгенерированного приложения.

Перед P4 выбрать и испытать конкретный первый web-профиль, а не считать пример Vue/Node или Vue/.NET окончательным решением. Перед P7 выбрать поддерживаемую авторизацию создания GitHub-репозитория и проверить разрешения аккаунта. Перед P8 определить формат отдельного переноса проекта и ограничения объёма.

Пока эти решения не приняты, действует: сохранение черновика без технического выбора; локальная работа без GitHub; ручное подтверждение требований и внешней публикации; ограниченный доступ только к выбранной папке. Реализацию этапов запускать отдельными задачами после рассмотрения обновлённых ТЗ.
