# Этап 3: поиск и хранение библиотеки

Проверено 17 октября 2026. Работа касается локальной библиотеки материалов; провайдер памяти OpenClaw, модели, Telegram и корпоративные настройки не меняются.

## Что изменилось

- SQLite 3.53.2 из установленного better-sqlite3 12.11.1 поддерживает FTS5 trigram с `case_sensitive 1`. Новых пакетов и серверов нет.
- `library_contents` хранит уникальный ограниченный текст, SHA-256 и результат `toLocaleLowerCase("ru")`. SHA-256 индексирует кандидатов дедупликации; перед объединением всегда проверяется точное равенство текста. Полного текстового B-tree в рабочей схеме нет.
- Каждый `library_items` сохраняет собственные ID, agentId, kind, title, source, locator, chars, created_at. Одинаковый текст из двух источников остаётся двумя результатами со своими ссылками; одинаковый текст разных агентов не расширяет доступ. Удаление последней ссылки удаляет содержание и FTS запись триггером.
- Запрос от трёх Unicode codepoints использует FTS-кандидатов и прежнюю точную проверку подстроки с прежними фрагментами/offset. Запрос заключён в FTS phrase, кавычки экранированы, пользовательские операторы не исполняются. RU/TG/EN используют одинаковый JS folding при добавлении, миграции и поиске.
- Короткий запрос и запрос с NUL используют точную ограниченную проверку последних 500 материалов. Если остаются непроверенные материалы, `partial=true`. Предел результатов 20 также выставляет partial при обнаружении 21-го совпадения. `searched` теперь означает число точно проверенных кандидатов; пустой запрос ничего не читает и возвращает 0.
- Для индексного запроса предел 500 относится к кандидатам, а не к последним 500 материалам корпуса. Старый редкий материал находится за этим прежним пределом. Для очень частого запроса результат всё ещё ограничен, о чём сообщает partial.

## Обновление и откат

`0008_library_search.sql` переносит существующие тексты, восстанавливает базовую FTS структуру; `openDb` заполняет Unicode folded/hash пакетами по 100 в транзакции. Если процесс прерван после SQL миграции, следующий запуск снова видит NULL folded и завершает заполнение. BFF начинает обслуживать запросы после завершения. Ошибка миграции закрывает соединение и останавливает открытие, не создаёт видимость готового индекса.

Очередь незаполненных строк обслуживает partial index `library_contents_pending_idx ON library_contents(id) WHERE folded IS NULL`. `EXPLAIN QUERY PLAN SELECT id, text FROM library_contents WHERE folded IS NULL LIMIT 100` подтверждает `SCAN library_contents USING INDEX library_contents_pending_idx`: каждый пакет читает оставшуюся очередь, без повторного сканирования уже обработанного префикса; при готовой базе индекс пуст. Миграционный тест переносит 206 уникальных текстов, проверяет заполнение всех folded/hash, поиск последнего пакета, выбор partial index, полный откат и повторное обновление.

Старый столбец `library_items.text` оставлен для обратной миграции, но после обновления содержит пустую строку. **Нельзя просто переключить бинарник на старую версию**: старый код будет искать в пустом столбце. Для отката 0008, пока это последняя миграция, нужно остановить BFF, сделать согласованную резервную копию SQLite вместе с WAL и выполнить файл `apps/bff/drizzle/rollback-library-search.sql` на этой базе. Скрипт сначала возвращает тексты, затем удаляет только добавленные структуры и запись 0008 в журнале. После этого можно запустить старый бинарник. Следующее обновление снова выполнит 0008, включая записи, добавленные старым бинарником после отката. Тест проверяет этот полный круг и равенство всех исходных полей.

Обновление может требовать дополнительного свободного места: перенос, временный текстовый индекс сопоставления, FTS и WAL. Файл SQLite после удаления данных обычно не уменьшается сам; VACUUM здесь автоматически не запускается. Это сознательный обмен диска на быстрый поиск. На большом корпусе миграция синхронная и задерживает старт; объём и окно обновления нужно учитывать.

## Измерения

Локальный синтетический корпус: 1200 материалов одного агента, каждый около 20 тысяч символов, 12 редких совпадений. 30 прогретых поисков, медиана и p95; файловые размеры снимались до закрытия соединения и checkpoint. Скрипт: `apps/bff/src/scripts/library-benchmark.ts`, запуск из `apps/bff`: `node node_modules/tsx/dist/cli.mjs --conditions=source src/scripts/library-benchmark.ts`; флаг `--unique` создаёт 1200 уникальных текстов вместо 100 повторяющихся. Это контрольный замер на данной машине, не SLA.

| Вариант | Совпадения / searched / partial | median / p95 | DB / WAL, байт |
| --- | --- | --- | --- |
| До правок, 100 уникальных текстов | 5 / 500 / true | 844.66 / 964.86 ms | 44 752 896 / 4 185 952 |
| После правок, 100 уникальных текстов | 12 / 12 / false | 3.54 / 3.92 ms | 10 391 552 / 4 494 952 |
| После правок, 1200 уникальных текстов | 12 / 12 / false | 14.12 / 21.40 ms | 119 906 304 / 5 702 112 |

Экономия места доказана только на повторяющемся корпусе. Для уникальных текстов folded и FTS увеличивают объём; обещания общей экономии диска нет. Первый вариант с `UNIQUE(text)` занимал 165 965 824 байта DB на уникальном корпусе; замена на SHA-256 B-tree убрала около 46 MB этого расхода. Уникальный корпус всё равно заметно больше исходного хранения текста без индекса.

## Проверки

15 тестов в `library-index.test.ts` и `library-budget.test.ts` прошли. Включены поиск старого материала за 600 новыми, RU/TG/EN, emoji, кавычки, проценты, подчёркивание, NUL, точные фрагменты, короткий bounded fallback, partial для 21-го результата, границы агентов, все источники и locator при дедупликации, удаление последней ссылки и повторное добавление, миграция старых данных, повторный запуск, полный откат и повторное обновление после legacy insert. BFF TypeScript проверен вне ограничений sandbox: успешно. Живой контейнер и пользовательская база этим заданием не изменялись.
