# Этап 3: производительность и хранение личного режима

Проверено 17 октября 2026. Изменения исходников сохранены вместе с незакоммиченными этапами 1–2. Личный стек, пользовательская база, папки, модели и Telegram-боты не изменялись; коммит, push и развёртывание не выполнялись.

## Результат

- Библиотека: FTS5 trigram сокращает число проверяемых текстов; дедупликация сохраняет отдельные источники и границы агентов. SHA-256 служит индексом кандидатов, перед объединением сравнивается текст. Короткие запросы сохраняют ограниченный точный поиск с явным `partial`. Миграция возобновляет заполнение Unicode folded/hash пакетами по 100; partial index ускоряет выбор оставшихся строк. Откат требует остановленного BFF, согласованной резервной копии и специального SQL, поскольку прежний текстовый столбец после переноса пуст.
- Синхронизация папок: ограниченный процессный кэш метаданных уменьшает чтение и хэширование неизменных файлов. Перед переносом обе стороны перечитываются; полная проверка повторяется не реже пяти минут. При смене режима кэш сбрасывается. Оптимизация включена только при подтверждённом личном режиме. Существующая база без выбранного пространства трактуется как personal по прежнему поведению SpaceService; ошибка чтения базы или неизвестный режим отключают кэш.
- Обзор: страницы истории и каталога расписаний загружаются по поддержанному Gateway `offset`. Предел — 50 страниц по 200 строк на метод и общий бюджет 8 секунд. Неполнота показывается явно, процент успешных запусков скрывается; неизвестные/удалённые задачи получают отдельное пояснение. Single-flight polling исключает наложение запросов и применение ответа прежнего периода.
- Система: личный режим показывает логический размер видеооригиналов и прежних версий файлов, свободное место, резервации загрузок и ручную квоту новых видео. Очистка требует просмотра точного списка и подтверждения одноразового токена на пять минут; клиентские пути не принимаются. Рабочие файлы, заметки и расшифровки сохраняются. Обнаруженные изменения и ошибки удаления оставляют quarantine-файл с показанным относительным путём, в том числе после перезагрузки интерфейса.
- Очередь видео: сохранённые ожидающие задания возобновляются после готовности Gateway; прерванные выполнявшиеся задания автоматически не повторяются. Остановка блокирует дальнейшее продвижение очереди и обращения к закрытой базе.

## Проверка интерфейса в браузере

Production build был открыт через временный Vite preview на 127.0.0.1:4173 в отдельном headless Chrome с Playwright из установленного bundled runtime. Все `/api/**` ответы подменены фиксированными данными: настоящий BFF, личные тома и Docker cleanup API браузером не вызывались. Первичный MCP браузер отказал из-за занятого профиля; использован отдельный процесс, чужие браузеры не закрывались.

Проверены реальные отрисовка и действия: preview содержит выбранный файл; удаление недоступно без checkbox и доступно после него; запрос cleanup содержит только token и confirm; предупреждение и путь retained-файла видны после результата и после reload; 120 MiB отправляются как 125 829 120 Б; неизвестные размер и число файлов отображаются тире; при ширине 390 px горизонтального overflow нет; в company режиме storage отсутствует. В обзоре при неполной истории показаны оба пояснения (partial и неизвестные задачи), успешные запуски — тире вместо процента. Итоговый повтор этих assertions прошёл. Временный браузер и preview остановлены после проверки.

Это проверка интерфейса с mock API, **не удаление файлов с пользовательского диска**. Операции файловой системы проверены отдельными Linux тестами исключительно на временных fixtures.

## Практические ограничения

Квота учитывает управляемые bridge загрузки и резервации; произвольный внешний процесс может увеличить диск. Неизвестный учёт блокирует новые загрузки при установленной квоте. Quarantine остаётся для ручного разбора; размер логический и не равен освобождённым физическим байтам при hard links. Метаданные и held directory handles обнаруживают наблюдаемые изменения и не дают перенаправить путь за утверждённое дерево, но не обещают абсолютную атомарность против писателя того же inode в последнем окне проверки. История cron по offset не является атомарным снимком меняющейся базы Gateway.

Чистая установка, миграция пользовательской базы в работающем стеке, длительная нагрузка и реальные Windows bind mounts не проверялись. До развёртывания библиотечной миграции нужна согласованная резервная копия SQLite/WAL и окно на перенос/дополнительное место.
