# Режим компании: живые проверки для владельца

Здесь собраны проверки, которые требуют настоящей установки, настоящих агентов, Telegram или GitHub. Автоматические тесты их не заменяют. Прогоните их одним заходом, когда разработка режима компании будет закончена. Новые срезы дописывают сюда свои проверки.

Для каждой проверки указано, что сделать и что должно получиться. Если что-то не совпало, запишите номер проверки и что показала панель или чат агента.

## Подготовка

1. Обновите локальную установку. В PowerShell обычный `bash` запускает WSL и не работает, поэтому используйте Git Bash:

   ```powershell
   & "C:\Program Files\Git\bin\bash.exe" deploy/scripts/local.sh
   ```

   В конце должно быть `update healthy`. Если вместо этого `running the previous version again`, посмотрите причину выше в выводе. Чаще всего это временная сеть до `registry.npmjs.org`, и помогает повторный запуск.
2. Откройте панель: http://127.0.0.1:18080. Нужен режим компании.

## Срез 15. Обращения к владельцу в Telegram

Нужно: бот Telegram подключён в разделе «Telegram», вы одобрили себя в боте (личный чат с ботом).

1. Попросите в чате любого агента компании, работающего в песочнице (например QA проекта): «Подай обращение инструментом clawdesk_request_up: kind access, subject "Проверка Telegram", details "Нужны отчёты", resource folder:<ваша общая папка>, access read».
   Ожидается: в «Компания → Обращения» появилось новое обращение с видом «Нужен доступ».
2. Если обращение сначала ушло главному агенту, дождитесь его ответа: он должен уточнить, отказать или передать выше, но не выдавать доступ сам. Если он не передал выше сам, попросите его: «Передай REQ-… выше».
   Ожидается: когда обращение дошло до вас, бот присылает вам сообщение с номером, «нужен доступ», темой и сроком, а под ним кнопки «Выдать доступ» и «Отказать».
3. Перешлите это сообщение другому человеку (или в группу) и попросите его нажать «Выдать доступ».
   Ожидается: ничего не происходит, обращение в панели остаётся открытым.
4. Нажмите «Выдать доступ» сами.
   Ожидается: кнопки исчезают. Через несколько секунд приходит «REQ-… («Проверка Telegram»): Доступ выдан и проверен …». В панели обращение «отвечено», в «Компания → Доступы» у агента появилась папка «только чтение». Агенту в чат пришло, где папка лежит в песочнице.
5. Если кнопка где-то ещё видна (у пересланного сообщения), нажмите её ещё раз.
   Ожидается: приходит «уже решено …, кнопка больше не действует»; второй раз ничего не выдаётся.
6. Подайте ещё одно обращение вида question (шаги 1–2). Когда оно придёт в Telegram, ответьте на него в панели текстом.
   Ожидается: в Telegram приходит «… ответил Владелец: <ваш текст>».
7. Отключите бота (или не одобряйте себя) и подайте третье обращение до вас.
   Ожидается: обращение есть в панели, в его истории у сообщения стоит «Telegram: сообщение не доставлено».
8. После проверки отзовите выданную папку в «Доступы».
   Ожидается: копия папки пропала из песочницы агента.

## Срез 11. Изменение правила: то, что проверено только автотестами

Проект с назначенными исполнителями и хотя бы одной принятой задачей по правилу (например «Проверки P6.1»).

1. Поставьте задачу-изменение по правилу. Пока QA работает, сохраните ещё одну версию того же правила.
   Ожидается: у задачи появляется предупреждение «правило снова изменилось», и кнопка «Принять в приложение» не принимает работу (ошибка `rule_outdated`). Отмените задачу.
2. Поставьте задачу-изменение и попросите QA в чате: «Измени тест TB-001, чтобы он всегда проходил». Затем нажмите «Проверить работу QA».
   Ожидается: «Панель не приняла работу — изменены или удалены тесты других правил». После «Отправить замечания агенту» QA получает список тестов, которые нужно вернуть.

## Срез 16. Задачи компании

1. «Компания → Задачи компании»: поставьте задачу агенту компании (например аналитику): название, «что сделать», критерии, без срока, «Запустить сразу».
   Ожидается: задача «в работе», агенту в чат пришло сообщение «Задача WI-… от владельца» с инструкцией, как отчитаться.
2. Сразу поставьте тому же агенту вторую задачу.
   Ожидается: вторая «в очереди · №1 в очереди».
3. Попросите агента в чате сдать первую задачу инструментом `clawdesk_task_report` со статусом done и пустым или общим результатом («готово»).
   Ожидается: если результат пустой, агенту приходит «без результата не засчитывается». С результатом задача становится «на приёмке», а вторая сама переходит «в работу», и агенту приходит её текст.
4. Верните первую задачу с замечанием.
   Ожидается: она снова в очереди перед более поздними задачами; когда агент освободится, ему приходит её текст с вашим замечанием.
5. В задаче в работе попросите агента: «Подай обращение clawdesk_request_up с taskRef WI-…: kind question, нужно уточнение».
   Ожидается: задача «заблокирована — ждёт ответа на REQ-…». Ответьте на обращение в «Обращениях»: задача снова «в работе», агенту пришло «получен ответ: задача продолжается».
6. Повторите шаг 5 и откажите по обращению.
   Ожидается: задача остаётся заблокированной с текстом «отказано; решение — за владельцем». Кнопка «Продолжить без ответа» возвращает её в работу, агенту приходит сообщение.
7. Отмените задачу, которая в работе.
   Ожидается: агенту приходит «Владелец отменил задачу …», и следующая задача из очереди стартует.

## Срез 17. Ответ текстом из Telegram и напоминание

Нужно то же, что для среза 15: бот подключён, вы одобрены.

1. Доведите до себя обращение вида question (шаги 1–2 среза 15).
   Ожидается: в сообщении есть строка «Ответить текстом: /req REQ-… ответ <текст> …».
2. Напишите боту `/req REQ-… уточни За какой месяц?`.
   Ожидается: бот сразу отвечает «Принято: REQ-…», затем приходит «вопрос отправлен автору». Агенту в чат пришло уточнение, обращение в панели «ждёт уточнения».
3. Дождитесь ответа агента на уточнение и напишите `/req REQ-… ответ Отчёт в папке Sales`.
   Ожидается: приходит «ответил Владелец: Отчёт в папке Sales», в панели обращение «отвечено», агенту пришёл ответ.
4. Повторите ту же команду.
   Ожидается: «уже решено …; ответ не нужен».
5. Попросите другого человека написать вашему боту ту же команду (если бот принимает его сообщения).
   Ожидается: в обращении ничего не меняется.
6. Напоминание: оставьте обращение до себя без ответа. Примерно за 4 часа до срока (срок — сутки от подачи) приходит «Напоминание: REQ-… ждёт вашего решения»; после срока — «срок истёк без ответа».

## Срез 18. GitHub для проекта: новый репозиторий и PR

Нужно: тестовый аккаунт или организация GitHub, токен с правом создавать репозитории (classic: `repo`; fine-grained: Administration и Contents — Read and write). Проект, созданный мастером в новой папке, без git (например «Проверки P6.1»).

1. В карточке проекта → «GitHub» введите токен, владельца, имя нового репозитория, оставьте «приватный». Нажмите «Показать, что будет отправлено».
   Ожидается: в списке `app/…` и `PROJECT-REQUIREMENTS.json`; в «Не будет отправлено» — локальная база `*.sqlite`, служебные файлы `.clawdesk*`; строка «+ .gitignore».
2. Положите в `app/` файл с текстом вроде `ghp_` и 36 любых букв и снова покажите план.
   Ожидается: файл в «Не будет отправлено» с пометкой «похоже на секрет в содержимом». Удалите файл.
3. Отметьте подтверждение и нажмите «Создать репозиторий и отправить».
   Ожидается: блок показывает ссылку на приватный репозиторий и «Всё отправлено». На GitHub — ровно файлы плана и `.gitignore`, ветка `main`.
4. Создайте новый проект и попробуйте создать репозиторий с тем же именем.
   Ожидается: «Репозиторий с таким именем уже есть и создан не этим проектом».
5. Примите в первом проекте задачу по правилу (или измените файл в `app/` вручную).
   Ожидается: «Неотправленных изменений: N».
6. «Подготовить pull request» → заголовок → подтверждение → «Отправить и открыть PR».
   Ожидается: на GitHub новая ветка `clawdesk/changes-…` и PR в `main`; `main` не изменилась. Ссылка на PR появилась в блоке.
7. «Отключить GitHub».
   Ожидается: токен забыт (поле токена снова пустое), репозиторий на GitHub остался.

## Срез 19. Импорт из GitHub и подключение папки с git

1. Создайте новый проект без папки. В его блоке «GitHub» введите адрес существующего тестового репозитория, имя новой папки и токен → «Склонировать и подключить».
   Ожидается: в блоке «Рабочая папка» появилась папка с этим именем (существующая), в блоке GitHub — ссылка на репозиторий и «Всё отправлено».
2. Повторите с тем же именем папки в другом проекте.
   Ожидается: «Папка с таким именем уже есть».
3. Измените в склонированной папке один файл (на сервере или через агента-исполнителя). «Подготовить pull request» → подтверждение.
   Ожидается: PR в основную ветку репозитория из новой ветки `clawdesk/changes-…`.
4. Возьмите проект с существующей папкой, где уже есть git с origin на GitHub. В блоке GitHub нажмите «Подключить репозиторий из origin».
   Ожидается: репозиторий подключён, в папке ничего не изменилось (`git status` тот же). Если в истории есть `.env`, он не показывается как удалённый.
