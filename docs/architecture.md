# Агентная панель на OpenClaw — архитектура и план MVP

Oct 11, 2026 · @Khusrav

## Цель и принятые решения

Продукт — open-source self-hosted панель, где обычный человек без терминала за 10 минут поднимает главного ИИ-агента, подключает к нему свои сервисы и Telegram, а потом создаёт младших агентов (диетолог, тренер, YouTube, команда проекта). Ядро — OpenClaw; наша часть — понятный UI, шаблоны и логика «главный → младшие».

Два режима при первом входе:

- **Личный ассистент** — дела, план, финансы, питание, тренировки.
- **Управление проектами компании** — репозитории, ТЗ, дизайн, команды агентов по проектам.

Зафиксированные решения:

| # | Решение | Следствие для кода |
| --- | --- | --- |
| 1 | Гибридный доступ к данным: младший агент читает свои источники напрямую, к главному обращается только за остальным | В модели агента есть явный список источников и флаг «может спрашивать главного» |
| 2 | Sandboxing включён для всех младших агентов | Docker на хосте обязателен; workspace агента монтируется в песочницу |
| 3 | Self-hosted: один экземпляр = один пользователь или одна команда | Нет мультитенантности в нашем коде; один Gateway на установку |
| 4 | Каждый пользователь подключает свой ключ или подписку модели | Онбординг содержит шаг «подключить модель»; мы ключи не храним и не раздаём |
| 5 | OpenClaw — зависимость, не форк; версия зафиксирована | Версия — в `deploy/openclaw.version` (было `2026.8.1`); `@openclaw/gateway-client` / `@openclaw/gateway-protocol` той же версии, `--save-exact`, копии сверяет `scripts/openclaw-version.mjs check`. Обновление — пулл-реквестом от ежедневного бампа с контрактным тестом на живом Gateway (README, «Обновление OpenClaw») |
| 6 | Свой UI для простых пользователей | Встроенный Control UI OpenClaw не показываем пользователю; он остаётся инструментом отладки |

Лицензия нашего репозитория — MIT (как у OpenClaw); файл LICENSE OpenClaw сохраняется в зависимостях.

## Общая схема

&#91;embedded content: схема системы · админка, BFF, Gateway, внешние сервисы\]

Админка говорит только с BFF; BFF — единственный клиент Gateway. Telegram идёт напрямую в Gateway, который по топику выбирает агента. Подключения к сервисам и ключ модели живут внутри Gateway.

## Компоненты и стек

Три процесса в одном `docker compose`: веб-админка, тонкий бэкенд (BFF) и OpenClaw Gateway. Браузер никогда не ходит в Gateway напрямую: device-токен и секреты живут только в BFF.

| Компонент | Стек | Отвечает за |
| --- | --- | --- |
| `apps/web` — админка | Vue 3, TypeScript, Vite, Pinia, Vue Router, vue-i18n (ru / en / tg), UI-кит (Naive UI или PrimeVue) | Экраны, мастера, чат с агентом, конструктор агентов |
| `apps/bff` — бэкенд панели | Node 24 LTS, Fastify, `@openclaw/gateway-client` 2026.8.1, Drizzle + SQLite, zod | Вход в панель, наши метаданные, превращение действий UI в цепочки RPC, прокси событий в браузер |
| OpenClaw Gateway | пакет `openclaw` 2026.8.1, как зависимость | Агенты, сессии, память, cron, каналы (Telegram), плагины, sandbox |
| Docker на хосте | Docker Engine | Песочницы младших агентов |

Почему BFF на Node, а не на ASP.NET: официальный клиент и TypeBox-схемы протокола есть только для npm, а общие типы с фронтом дают один язык на весь репозиторий.

Структура монорепо (pnpm workspaces):

```
apps/
  web/                 # Vue 3 админка (одна сборка для браузера и десктопа)
  bff/                 # Fastify + gateway-client
    src/gateway/       # обёртка над RPC, реконнект, подписки
    src/provision/     # «создать агента» = цепочка RPC + откат
    src/db/            # Drizzle-схема, миграции
  desktop/             # Tauri 2
    src/               # экраны лаунчера (Vue): серверы, мастер установки
    src-tauri/         # Rust: SSH (russh), туннель, keychain, трей, updater
packages/
  shared/              # типы и zod-схемы общие для web, bff и desktop
  ui/                  # общие Vue-компоненты для web и лаунчера
  templates/           # шаблоны агентов: SOUL.md, AGENTS.md, skills, пресеты cron
deploy/
  docker-compose.yml
  install.sh           # установка на Ubuntu; его же запускает мастер десктопа
.github/workflows/
  release.yml          # по тегу: установщики Tauri + Docker-образ панели
```

## Десктоп-приложение

Десктоп — на Tauri 2: установщик на порядок меньше, чем у Electron, потому что внутри нет своего Chromium, а Vue работает без изменений. Агенты на компьютере не работают: всё живёт на сервере, поэтому расписания и Telegram работают, даже когда компьютер выключен.

&#91;embedded content: доступ к панели · десктоп, браузер, Telegram\]

Десктоп ходит на сервер через SSH-туннель, поэтому ему не нужны домен и открытые порты. Домен с HTTPS нужен только тем, кто хочет заходить ещё и из браузера.

Что умеет десктоп, чего нет в браузере:

| Функция | Как сделано |
| --- | --- |
| Мастер «Установить на сервер» | Пользователь вводит IP и пароль или ключ сервера; Rust-часть (crate `russh`) заходит по SSH, запускает `install.sh` и показывает лог шагами. После установки парольный вход заменяется ключом |
| Подключение без домена | SSH-туннель с локального порта на панель внутри сервера |
| Несколько серверов | Список серверов в лаунчере (личный, компания) |
| Хранение ключей и токена входа | Системное хранилище (Keychain, Windows Credential Manager, Secret Service) |
| Уведомления | Нативные уведомления об одобрениях и ошибках агентов, иконка в трее |
| Автообновление | `tauri-plugin-updater` по релизам GitHub |

Устройство внутри:

- **Лаунчер локальный, панель с сервера.** В установщике лежат только экраны лаунчера (список серверов, мастер установки). После подключения окно открывает панель с сервера. Поэтому UI в десктопе и в браузере всегда одной версии, и обновлять десктоп ради каждой правки UI не нужно.
- **Один код UI.** `apps/web` знает, где запущен (`window.__TAURI__`), и только в десктопе показывает нативные кнопки (трей, уведомления).
- **Безопасность.** Доступ страницы с сервера к нативным командам ограничен capabilities Tauri: только уведомления и трей, без файлов и shell. SSH вызывают только локальные экраны лаунчера.

Сборка: при пуше тега `v*` GitHub Actions (`tauri-apps/tauri-action`) собирает `.exe` / `.msi` для Windows, `.dmg` для macOS, `.AppImage` / `.deb` для Linux и кладёт их в GitHub Release. Там же собирается Docker-образ панели для сервера. Без подписи Windows и macOS будут предупреждать при установке. Подпись Apple стоит $99 в год, для Windows нужен сертификат подписи кода. Для v0.1 можно без подписи.

## Модель данных

Источник истины для работы агентов — конфиг OpenClaw; наша SQLite хранит только то, чего OpenClaw не знает (шаблон, подписи для UI, каталог источников, команды). Связка — по `agentId`. При старте BFF сверяет свою базу с `agents.list` и `cron.list` и помечает расхождения. Секреты (ключи модели, OAuth-токены, токен бота) лежат только в OpenClaw, у нас — статус.

| Сущность | Ключевые поля | В OpenClaw это |
| --- | --- | --- |
| `Space` — установка | `id`, `mode` (personal / company), `name`, `locale`, `timezone` | Один Gateway |
| `PanelUser` | `id`, `email`, `passwordHash` или passkey, `role` (owner / member) | Нет (только наш вход) |
| `Agent` | `id` (= agentId, slug), `role` (main / specialist / team\_member), `parentId`, `teamId?`, `templateId`, `displayName`, `avatar`, `purpose`, `model`, `canAskMain`, `sandbox`, `status` | `agents.entries.<id>` + файлы workspace `SOUL.md`, `AGENTS.md`, `USER.md` |
| `DataSource` | `id`, `kind` (notion / gmail / gdrive / github / figma / folder), `connectorRef`, `scope`, `status` | Плагин или MCP-сервер, авторизованный у главного агента |
| `AgentSourceGrant` | `agentId`, `sourceId`, `access` (read / write), `scope` (подмножество) | Allowlist инструментов и skills агента + монтирование папок в sandbox |
| `Schedule` | `id`, `agentId`, `cron`, `tz`, `prompt`, `deliverTo`, `openclawCronId`, `enabled` | Cron-задача (`cron.add`) с доставкой в канал |
| `ChannelBinding` | `id`, `agentId`, `channel`, `accountId`, `peerKind`, `peerId`, `topicId?` | `bindings[]` или `channels.telegram.groups.<chat>.topics.<topic>.agentId` |
| `Team` (режим company) | `id`, `name`, `repoUrl`, `telegramGroupId`, участники через `Agent.teamId` | Группа агентов + форум-группа Telegram |
| `ModelCredentialStatus` | `provider`, `method` (api\_key / setup-token), `ok`, `checkedAt` | Auth-профиль агента (секрет там) |
| `AuditEvent` | `at`, `actor`, `action`, `target`, `result` | Дополняется audit-леджером Gateway |

Пример того, во что BFF превращает агента «Диетолог» (имена ключей взяты из документации; точную форму сверить со схемой `gateway-protocol` 2026.8.1):

```json5
{
  agents: {
    ownership: "explicit",
    entries: {
      main:      { workspace: "~/.openclaw/workspace" },
      dietitian: {
        workspace: "~/.openclaw/workspace-dietitian",
        skills: ["nutrition-plan", "shopping-list"],   // заменяет defaults, не сливается
        tools: { agentToAgent: { send: ["main"] } },      // может писать только главному
        sandbox: { mode: "all" }
      }
    }
  }
}
```

## Как агенты работают вместе

&#91;embedded content: запрос к младшему агенту · когда подключается главный\]

Младший агент сначала отвечает по своим данным; главного он спрашивает, только когда нужного не хватает, и получает короткую выжимку, а не сырые файлы.

Правила, которые выставляет BFF при создании агента:

1. **Прямой доступ.** Источники из `AgentSourceGrant` монтируются в sandbox или открываются инструментами плагина; остальное агент не видит.
2. **Вопрос главному.** Только если `canAskMain = true`: `tools.agentToAgent.send = ["main"]`. В `AGENTS.md` младшего прописано: спрашивать конкретный факт или путь, не «пришли всё».
3. **Ответ главного.** В `AGENTS.md` главного: отвечать выжимкой до N строк и путями к файлам, к которым у младшего есть доступ.
4. **Файл в чате младшего.** Младший сохраняет его в свой workspace. Если файл нужен другим (анализы, план), он передаёт главному в режиме `notify`, и тот кладёт его в общую папку.
5. **Кто кому пишет.** Главный — всем; младшие — только главному. В MVP младшие друг другу не пишут; в команде проекта PM может писать своей команде.
6. **Деньги на токены.** У младших по умолчанию модель дешевле, у главного — сильная. Фоновые запросы — `sessions_send` с `timeoutSeconds: 0`, чтобы не держать сессию.
7. **Тяжёлая разовая задача.** Главный запускает временного под-агента через `sessions_spawn`; глубина ограничена `maxSpawnDepth: 2` (по умолчанию 5).
8. **Sandbox.** У младших — всегда. У главного exec на хосте только через одобрение.

Источники: [Session tools](https://docs.openclaw.ai/concepts/session-tool), [Multi-agent routing](https://docs.openclaw.ai/concepts/multi-agent), [Sandboxing](https://docs.openclaw.ai/gateway/sandboxing).

## Экраны админки и RPC-вызовы

Браузер дёргает REST-эндпоинты BFF, а BFF выполняет цепочку RPC в Gateway и при ошибке откатывает уже сделанные шаги. События Gateway (ответ агента потоком, инструменты, одобрения) BFF пересылает в браузер по своему WebSocket.

| # | Экран | Что делает пользователь | RPC в Gateway |
| --- | --- | --- | --- |
| 1 | Первый запуск | Создаёт логин владельца; панель проверяет Gateway | Рукопожатие `connect` (роль operator, scopes `read` + `write` + `approvals` + `admin`), методы статуса |
| 2 | Выбор режима | «Личный ассистент» или «Проекты компании», язык, часовой пояс | Только наша база |
| 3 | Подключить модель | Вставляет API-ключ или setup-token, выбирает модель | Семейства secrets / wizard, `config.patch` (модель по умолчанию), проверка через методы models |
| 4 | Главный агент | Имя, характер, «что обо мне знать» | `agents.create` (или `agents.update` для `main`) → `agents.files.set` × 3 (`SOUL.md`, `AGENTS.md`, `USER.md`) |
| 5 | Источники данных | Нажимает «Подключить Notion / Google / GitHub / Figma», проходит OAuth | Семейство plugin management (установить, включить), wizard плагина для OAuth; MCP-серверы через `config.patch` |
| 6 | Telegram | Вставляет токен бота, пишет боту, подтверждает пару в панели | `config.patch` (`channels.telegram`), методы channels (статус, проба), методы pairing (одобрить отправителя) |
| 7 | Мои агенты (главная) | Видит дерево «главный → младшие», статус, ближайший запуск | `agents.list`, `sessions.list`, `cron.list` |
| 8 | Конструктор агента (мастер из 4 шагов) | Шаблон → цель своими словами → к каким данным доступ → расписание и канал | `agents.create` → `agents.files.set` → `config.patch` (skills, `tools.agentToAgent`, sandbox, bindings) → `cron.add`; при ошибке `agents.delete` |
| 9 | Чат с агентом | Пишет, прикладывает фото и файлы, видит ответ потоком | `chat.send`, подписка на события сессии, история через `sessions.*`; для фоновых задач `agent` + `agent.wait` |
| 10 | Расписания | Включает, правит время, жмёт «Запустить сейчас» | `cron.list`, `cron.add`, `cron.update`, `cron.remove`, `cron.run` |
| 11 | Команды проектов (company) | Создаёт команду под репозиторий, выбирает роли, привязывает Telegram-группу | `agents.create` × N, `agents.files.set`, `config.patch` (топики → `agentId`), `cron.add` |
| 12 | Одобрения | Разрешает или запрещает опасные действия агента | Методы approvals (список, решение) |
| 13 | Расход | Видит токены по агентам и дням | `sessions.usage`, методы usage |
| 14 | Настройки и журнал | Бэкап, обновление, история действий | `config.get`, ledger RPC (аудит), методы update |

Имена `agents.*`, `cron.*`, `config.*`, `chat.send`, `agent`, `agent.wait`, `sessions.*` взяты из документации. Для строк, где названо только семейство (secrets, plugins, channels, pairing, approvals, update), точные методы взять из [RPC methods](https://docs.openclaw.ai/gateway/protocol/rpc-methods) на первом шаге MVP. Если для какого-то шага RPC нет, BFF вызывает CLI `openclaw …` в контейнере Gateway.

## Шаблоны режимов

Шаблон — папка в `packages/templates` с `template.json` (поля мастера, skills, пресеты cron, нужные источники) и заготовками `SOUL.md` / `AGENTS.md` с плейсхолдерами. Любой может прислать свой шаблон пулл-реквестом — это главная точка роста open-source сообщества.

**Личный ассистент**

| Агент | Данные | Расписание по умолчанию | Канал |
| --- | --- | --- | --- |
| Главный ассистент | Все источники: Notion, Gmail, Google Drive, файлы | 08:00 план на день; 20:00 чек-ин; пн 09:00 адаптация плана | Личка Telegram |
| Диетолог | Папка «Питание», фото из чата, список покупок | 07:30 меню на день и что купить | Топик «Питание» |
| Тренер | Папка «Тренировки», дневник нагрузок | 06:30 тренировка дня; 21:00 что сделал | Топик «Тренировки» |
| Финансы | Память о тратах из чата (без банка) | Вс 20:00 итог недели | Топик «Финансы» |
| YouTube | Папка «Идеи», сценарии | По запросу | Топик «YouTube» |

Расписания — из твоего README; пользователь меняет их в мастере. Расписания тренера, диетолога и финансов — примеры для шаблона.

**Проекты компании**

| Агент | Данные | Что делает | Канал |
| --- | --- | --- | --- |
| Главный агент компании | Все репозитории, Google Drive с ТЗ, Figma, Notion | Знает, где что лежит; создаёт команды; сводка по проектам | Общий топик группы |
| PM проекта | ТЗ и дизайн своего проекта, issues | Разбивает задачи, ежедневный статус | Топик «PM» |
| Разработчик | Только репозиторий проекта, в отдельной ветке (managed worktree) | Меняет код, гоняет тесты, открывает PR | Топик «Dev» |
| Ревьюер | Репозиторий проекта, только чтение | Проверяет PR до человека | Топик «Review» |

Мерж в основную ветку и деплой — всегда человек; агенты доходят до PR.

## Безопасность и установка

Одна установка = одна граница доверия: все, кто входит в панель, должны доверять друг другу. От чужих защищают настройки ниже; для недоверяющих команд — отдельные установки.

Правила, которые панель выставляет сама:

- Gateway слушает только loopback / внутреннюю сеть compose; порт 18789 наружу не открывается.
- Наружу смотрит только панель, через HTTPS: Caddy с Let's Encrypt или Cloudflare Tunnel.
- У всех младших агентов sandbox включён, в песочницу монтируются только их workspace и выданные папки.
- Telegram: `dmPolicy` с парованием, `allowFrom` = владелец (и члены команды); в группах — allowlist групп.
- Опасные действия (exec на хосте, отправка писем, push) идут через экран «Одобрения» и кнопки в Telegram.
- Входящие письма, страницы и файлы — недоверенные данные (prompt injection); агенту с доступом к Gmail не даём инструменты записи без одобрения.
- Бэкап `~/.openclaw` + базы панели раз в сутки, только в приватное хранилище: там токены.

Установка для пользователя (Ubuntu LTS, от 2 ГБ RAM — как в README; с sandbox и несколькими агентами лучше 4 ГБ):

```bash
curl -fsSL https://<ваш-домен>/install.sh | bash
# ставит Docker, качает docker-compose.yml, спрашивает домен,
# поднимает panel + gateway и печатает ссылку на первый запуск
```

Всё остальное (модель, источники, Telegram, агенты) — в браузере. Обновление — новый тег образа панели, в котором зафиксирована проверенная версия OpenClaw; перед обновлением — бэкап и `openclaw doctor --fix`.

## План MVP

&#91;embedded content: план MVP · 5 этапов с проверками\]

Следующий этап не начинается, пока не пройдена проверка справа. Сроки не стоят: они зависят от твоего темпа.

Этап 0 по шагам — с него начинать в режиме кода:

- [ ] Поднять `openclaw@2026.8.1` в Docker, `openclaw onboard` вручную один раз
- [ ] Минимальный BFF: `connect` → парование устройства → сохранить `deviceToken` → `agents.list`

## Риски и что проверить первым

Самый большой риск — что часть настроек (логин модели, OAuth плагинов) доступна только через CLI, а не через RPC. Это проверяется спайком в этапе 0, до того как рисовать экраны.

| Риск | Чем проверить | Запасной путь |
| --- | --- | --- |
| Нет RPC для логина модели или OAuth плагина | Спайк: пройти онбординг только через RPC | BFF запускает `openclaw …` в контейнере Gateway и парсит вывод |
| Cron не стартует сам, пока сессия не «разбужена» (из README) | Тест: задача на +2 минуты после рестарта, без сообщений | Включить Heartbeat по умолчанию |
| Протокол меняется между версиями | Контрактные тесты BFF против живого Gateway в CI | Версия зафиксирована; обновление — отдельный PR |
| Главный агент становится узким местом по токенам | Экран «Расход»: доля токенов на запросы младших к главному | Расширить прямые доступы младшему; дешёвая модель для младших |
| Sandbox требует Docker и памяти | Запуск 5 агентов на сервере 2 ГБ | Рекомендовать 4 ГБ; иначе sandbox только для агентов с exec |
| Секреты попадут в браузер или логи панели | Ревью кода BFF + тест на редакцию логов | Секреты только write-only полями, назад — только статус |
